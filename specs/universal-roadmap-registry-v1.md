# Polaris Universal Roadmap Registry v1

Status: CANONICAL

## Objective
Nothing consequential in Polaris may exist only in conversation, memory, scattered prose, or an untracked branch. Every capability, invariant, domain, adapter, integration, migration, physical deployment, app surface, unresolved overlay, known blocker, and retirement path must resolve to a roadmap record or an explicit N/A classification.

## Roadmap states
DISCOVERED; SPECIFIED; PLANNED; READY; IN_PROGRESS; VERIFIED; DEPLOYED; OPERATING; DEGRADED; BLOCKED; DEFERRED; SUPERSEDED; RETIRED; IMPOSSIBLE; N_A; UNKNOWN.

UNKNOWN and BLOCKED require an explicit blocker/reason. DEFERRED requires a trigger/revisit condition. SUPERSEDED requires a successor. RETIRED requires preserved history/receipt where consequential.

## Roadmap record
Each consequential item should carry, at the cheapest adequate resolution:
ID; NAME; TYPE; OWNER; SCOPE; OBJECTIVE/REQUIREMENT; CURRENT_STATE; TARGET/SUCCESSOR_STATE; PARENT/DEPENDENCIES; BLOCKERS; AUTHORITY/SAFETY/PRIVACY gates where relevant; ENTRY_CONDITIONS; EXIT/VERIFICATION; NEXT_ACTION; DEFER/REVISIT trigger; SOURCE/PROVENANCE; VERSION/BRANCH/RELEASE if applicable; SUPERSEDES/SUPERSEDED_BY; PHYSICAL_DEPLOYMENT_GUIDE link where applicable; TEST/EVIDENCE receipt; COST/RESOURCE band where consequential; LAST_REVIEWED; INVALIDATION condition.

## Universal coverage
Roadmap all of the following where they exist:
- constitutional invariants, polar rules and anti-patterns;
- Reality/Evidence/External World State/Operative State/Successor State/Bearings/Execution machinery;
- semantic shapes, standards, ontologies and domain adapters;
- data/evidence ingestion, acquisition, provenance, CAS, Merkle, CRDT, rollups, sparse state, compression, caches, model foundry/router;
- Jarvis, Basecamp, AMOS, Scribe, Wayfinder and app surfaces;
- authority, privacy, identity, security and credentials;
- finance, legal, elections, products, resources, housing, land, ecology, weather, infrastructure and every other registered domain;
- GH, MH, Campus, workshop, garage, greenhouse, animals, landscape, utilities, vehicles, mobile field and physical deployment;
- integrations/providers/connectors and provider-independent fallbacks;
- tests, migrations, backfills, compatibility and deprecation work;
- unreleased overlays, missing source bytes, release-candidate debt, unknown exact historical semantics;
- user-requested capabilities not yet implemented;
- known removals, replacements, superseded doctrine and cleanup debt.

## Hierarchy
ROADMAP PORTFOLIO -> PROGRAM/CAPABILITY -> MILESTONE/SUCCESSOR STATE -> WORK PACKAGE -> VERIFICATION RECEIPT.
Do not explode trivial implementation details into permanent roadmap objects. Roadmap at the smallest level necessary to prevent loss, ambiguity, dependency blindness or false completion.

## Successor-state law
Roadmaps are state-transition maps, not task lists. Each item answers: current verified reality -> next reachable verified reality. Completion is the transition to a verified successor state, not activity performed.

## Dependency law
Roadmap dependencies form typed DAGs where direction matters. A parent cannot be promoted beyond the qualification state of required descendants/dependencies. Recursive Beta Closure applies where Beta qualification is claimed.

## Closure persistence
Recoverable execution failure does not erase roadmap intent or verified progress. Checkpoint completed work, preserve blockers, and resume from the smallest safe replay boundary. Strategy must change after repeated equivalent failures rather than loop indefinitely.

## Delta-only human projection
Default human roadmap view surfaces only:
WHAT CHANGED -> DIRECTION -> CONSEQUENCE/ACTION.
Stable roadmap background collapses. Full graph remains drillable.

## Reconciliation / mining law
Conversation mining, shared-chat mining, source recovery, repository audits and new discoveries must reconcile against the registry:
NEW -> ADD;
SAME -> LINK/DEDUPE;
REFINEMENT -> UPDATE;
CONFLICT -> PRESERVE + DISCRIMINATE;
SUPERSEDED -> TOMBSTONE/LINK;
UNKNOWN -> BLOCKER.
No recovered concept is considered propagated until its roadmap and owning canonical surfaces agree.

## Physical link
Any ROADMAP item with physical manifestation must resolve to the Universal Physical Deployment Guide Registry or explicitly classify why not.

## Release link
Every release candidate/version should declare which roadmap states changed and which roadmap debt remains. Missing underlying source bytes or unverified implementation remain blockers rather than being promoted by release naming.

## Self-pruning
Verified replacements must identify obsolete roadmap items for retirement. Completed, superseded and retired records remain historically queryable but leave the active working set.

## Anti-patterns
wishlist roadmap; giant undifferentiated backlog; conversation-only capability; branch-only capability; roadmap item with no owner; owner with no authority; milestone with no verification; perpetual IN_PROGRESS; DEFERRED with no trigger; UNKNOWN silently treated as planned; completed task mistaken for achieved state; duplicate roadmap entries for one capability; dependency-free fantasy dates; version label promoted to implementation evidence; roadmap becomes second truth store; physical deployable without deployment guide; retired item left active; stable background flooding the user.

## Final law
IF IT MATTERS, IT HAS A PLACE IN THE ROADMAP. IF IT IS NOT VERIFIED, THE ROADMAP MUST SAY WHAT IS MISSING. IF IT IS SUPERSEDED, THE ROADMAP MUST SAY BY WHAT.
