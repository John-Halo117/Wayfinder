# Polaris Physical Deployment Roadmap v1

Status: CANONICAL ROADMAP / NOT A PURCHASE LIST

## Objective
Deploy Polaris into physical reality in stages while preserving constitutional invariants: no premature hardware, no duplicated truth, no unnecessary dependencies, no authority creep, no permanent obligation before need.

Core law:
SOFTWARE CAPABILITY -> PROVEN NEED -> CHEAP INTERFACE/ROUTE -> MINIMUM ADEQUATE HARDWARE -> VERIFY -> EXPAND ONLY ON DELTA.

## Phase 0 — Software-first / no physical dependency
Goal: Polaris remains useful on ordinary existing hardware.
Minimum: phone/PC, repository, encrypted backups, manual data entry/import where adequate.
Exit: core models, authority, evidence, task execution, pithy projection, backup/restore, and offline/manual degradation all work without dedicated site hardware.
Do not buy yet: dedicated racks, sensors, cameras, robots, specialty servers, smart-home hardware.

## Phase 1 — Basecamp core
Goal: establish one canonical local digital core.
Minimum: reliable host, local storage, UPS where justified, secure network, backup target.
Capabilities: canonical state, CAS/evidence, service orchestration, identity/authority enforcement, local APIs, logs/receipts, backup/restore.
Exit: restore drill passes; single device loss does not destroy canonical state; services degrade gracefully without WAN.

## Phase 2 — Network / storage / security backbone
Goal: one standards-first campus digital spine.
Minimum: router/firewall, managed switching only where needed, Wi‑Fi coverage, segmented trust zones, NAS/NVR only when actual data volume requires them.
Reserve: conduit/pathways, power, rack/utility location, patching space before populating hardware.
Exit: local services reachable, least-authority segmentation proven, no cloud dependency for critical local functions, backup paths tested.

## Phase 3 — GH first physical node
Goal: make GH the first complete inhabited Polaris environment without turning it into a miniature MH.
Minimum endpoints: environmental sensing that changes action, life-safety interfaces, utility/water/power state where available, simple local controls, network edge, manual fallbacks.
Default: passive topology first; local actuation only for consequential needs.
Exit: GH can operate safely during Basecamp/WAN/control outage; critical state remains visible; user burden is lower than pre-Polaris baseline.

## Phase 4 — Campus backbone
Goal: connect shared physical infrastructure without centralizing every function.
Scopes: Campus Core, Utility Plant, Workshop, Garage, Greenhouse/Garden, Animal, Landscape/Water, Bulk Storage.
Add only as reality exists: well/water, PV/storage, wastewater, workshop equipment, greenhouse, animal systems, exterior sensors, package/exchange boundary.
Exit: semantic owner != deployment location is preserved; shared backbones have bounded failure domains; local manual operation remains possible where consequence warrants.

## Phase 5 — Edge nodes
Goal: distribute sensing/control/cache only where latency, offline operation, bandwidth, privacy, or failure locality justify it.
Edge node may provide: local sensor fusion, bounded automation, local cache, protocol bridge, temporary operation during Basecamp loss.
Must not become: independent truth owner, unbounded authority, silent permanent fork.
Exit: reconciliation is deterministic; node loss is local; reconnect does not create epistemic or authority conflict.

## Phase 6 — MH deployment
Goal: extend the same shared semantics into the long-term home without importing GH compression defaults.
Deploy: richer comfort/AV/environment endpoints, room/zone state, accessibility/service interfaces, hospitality and privacy controls where useful.
Keep canonical services shared; deploy point-of-use endpoints locally where frequency/consequence earns duplication.
Exit: MH remains usable manually; failure does not strand basic access, lighting, water, thermal safety, egress, or privacy.

## Phase 7 — Mobile / vehicle / field
Goal: carry bounded capability beyond the property.
Scopes: VEHICLE, PERSONAL_DEVICE, MOBILE_FIELD.
Capabilities: offline maps/data, vehicle state, field inspection/capture, preparedness inventory, temporary sensors, secure scoped credentials, delayed synchronization.
Exit: lost/stolen mobile node exposes minimal data/authority; canonical state survives; sync is delta-only.

## Phase 8 — Automation / robotics
Goal: automate only proven recurring burdens.
Admission: task is frequent/material; environment is sufficiently structured; failure is bounded; manual fallback exists where required; total administration falls.
Sequence: passive geometry -> manual mechanism -> assisted mechanism -> deterministic automation -> model-based automation -> robotics.
Exit: automation demonstrably deletes human administration/attention; maintenance and exception load remain below displaced labor.

## Phase 9 — Resilience / failover
Goal: survive realistic failures rather than duplicate everything.
Qualify by failure consequence x probability x recovery time.
Potential measures: UPS, local manual paths, spare critical commodity parts, alternate WAN, backup host/storage, offline credentials, emergency power/water visibility.
Exit: periodic failure drills prove recovery; backups are exercised; critical capability has known degraded states.

## Phase 10 — Mature self-pruning campus
Goal: deployment stops growing by default.
Continuously measure: active endpoints, unused sensors, bytes/compute/bandwidth, human attention events, maintenance, failure rates, unique information contribution, automation exceptions.
Demote/remove hardware and services that no longer discriminate consequential state or delete burden.

## Purchase gate
Before any physical purchase:
1. What requirement is unmet?
2. Can software/manual/passive geometry solve it?
3. Can a cheap route/interface be reserved instead of hardware installed?
4. Is an existing standard/commodity device adequate?
5. What canonical semantic owner will it report to?
6. What authority does it need — no more?
7. What happens when it fails/offlines/vendor disappears?
8. Can it be replaced without architectural rework?
9. What ongoing maintenance/attention does it add?
10. What existing burden does it delete?

Fail -> DEFER / RESERVE / DO NOTHING.

## Deployment topology
CANONICAL DIGITAL CORE
-> SHARED NETWORK/UTILITY BACKBONES
-> LOCAL EDGE ENDPOINTS
-> GH/MH/CAMPUS/VEHICLE/FIELD DEPLOYMENTS
-> PITHY HUMAN PROJECTIONS.

One truth, many endpoints. Local operation, shared semantics.

## Anti-patterns
Rack-before-requirement; sensor confetti; smart-home shopping spree; cloud-first critical control; edge-node sovereignty; duplicate databases per building; centralization that breaks local basic function; local duplication of expensive shared equipment; proprietary protocol lock-in; permanent conduit/hardware everywhere for hypothetical futures; automation before stable workflow; robot tax; dashboard proliferation; unused NVR/data accumulation; battery/UPS redundancy without failure model; Basecamp single point of physical survival; physical deployment outrunning documentation/authority/recovery tests.

## Final invariant
DEPLOY POLARIS AS REALITY EARNS HARDWARE. Preserve cheap interfaces/options early; install expensive stateful machinery late.
